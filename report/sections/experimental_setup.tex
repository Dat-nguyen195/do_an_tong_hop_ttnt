\section{EXPERIMENTAL SETUP}\label{sec:setup}
The evaluation asks: \textbf{RQ1}, how do the three selectors compare on the controlled candidate banks; \textbf{RQ2}, how many questions are asked and how do sessions terminate; and \textbf{RQ3}, what selection behavior is observed on the saved pools labeled as generated by two LLM backends? These are descriptive questions about a limited prototype, not tests of statistical superiority or general robustness.

\subsection{Synthetic Cases and Pilot Catalog}
The measured dataset is \path{config/ambiguity_benchmark.json}: 32 cases, with four variants in each of eight families. A variant contains an underspecified description, interface, seed inputs, candidate bank, reference code, and five initial evaluation inputs. The target interpretation varies across variants; for example, sorting targets may be ascending or descending. Table~\ref{tab:synthetic_families} lists these choices. The four variants in a family are related and are not independent real-world problems.

For the offline configuration, the runner shuffles each three-program bank using seed 3101, keeps three candidates, and saves the ordered pool. The reference implementation is available in the bank by construction. The experiment therefore evaluates selection when a useful candidate is available; it does not measure candidate-generation coverage on arbitrary tasks.

A separate file, \path{config/dataset_sample.json}, contains 15 pilot tasks. Eight are HumanEval-derived~\cite{humaneval}; five match MBPP task contracts~\cite{mbpp}; one is an adaptation of MBPP/534 and one has no verified upstream source. The pilot is used for baseline development and provenance audit, not for the 32-case result. Local tests are reduced or modified, so the catalog does not imply evaluation with either benchmark's official test suite.

The audit corrects two legacy IDs: \texttt{similar\_elements} maps to MBPP/2 and \texttt{find\_substring} to MBPP/91. \texttt{count\_upper} is treated as a local task, since MBPP/105 counts Boolean values. The local \texttt{search\_literal} returns a start index or $-1$, unlike MBPP/534's span result. \texttt{remove\_Occ} removes the first \emph{and} last occurrence. Upstream records, response hashes, source URLs, adaptation notes, and checks of the local tests accompany the catalog. These checks do not establish correctness on omitted upstream or unseen tests.

\subsection{Selectors and Shared Budget}
All three selectors receive the same ordered pool and the same retained evaluation inputs. \textsc{Direct-1} chooses the first code string. \textsc{First-Valid} chooses the first candidate admitted by the shared syntax, policy, duplicate, and top-level function-name checks. These checks do not establish full type/signature compatibility or semantic correctness. \textsc{Balanced} uses binary entropy, hard filtering, at most three questions, and at most eight probes per task. Semantic wording and soft belief updates are disabled in this experiment.

Direct-1 is a selector from a pool that may have required several generation requests; it is not a separate one-call or chain-of-thought experiment. Oracle Best-of-K is not included as a deployable method because it would select using evaluation labels. A requested pool limit of three does not guarantee three distinct generated programs; the live-labeled pilot pools contain two or three after deduplication.

\subsection{Probe Separation and Reference Oracle}
Before expected outputs are computed, the runner constructs the complete bounded probe set from seed inputs and mutations and removes exact matches from the evaluation inputs. The same retained inputs are used for every selector. For 32 cases, 33 of the initial 160 input instances are excluded, leaving 127 instances, or two to five per case. Each eight-case pilot retains 31 instances. Input disjointness prevents exact reuse of a probe as an evaluation input; related patterns and the hand-authored relationship between candidates and tests remain validity limitations.

On a question proposing output $y$ for input $x$, the oracle returns whether the reference program produces $y$ on $x$. The reference code and evaluation labels are not passed to candidate generation. Feedback is noiseless and is supplied by code, not human participants. The small retained test sets only assess finite-suite agreement.

\subsection{Recorded Backends and Configuration}
The saved pilot manifests identify \texttt{gemini-3.5-flash-lite} through the Gemini adapter and \texttt{qwen2.5-coder:32b} through an OpenAI-compatible endpoint. Qwen2.5-Coder is described in its technical report~\cite{qwen25coder}; the local tag alone does not pin a model-weight revision. These identifiers are reported as recorded, without claims about current service availability or model rankings. The primary controls are seed 3101, top-$K=3$, question budget three, probe budget eight, five-second execution timeout, and enabled execution caching.

There is one eight-task saved run per backend and no repeated-seed study. The offline run ID is \texttt{e6a84cf2098af752}; the two pilot IDs are \texttt{8be202264a584167} and \texttt{b6c988199ed7b1d5}. Their complete manifests, pools, checkpoints, and CSV files are included. Original live generation is not repeated during final verification: selection and evaluation are replayed from saved code. Provider request IDs, token usage, generation latency, and a pinned Qwen weight digest were not recorded, so exact regeneration of the original pools is outside the reproducibility claim.

\subsection{Metrics and Verification}
A case passes when its selected program passes every retained evaluation input. We report passed cases/total cases, question count, and termination reason separately. Having one candidate means convergence within a finite pool, not correctness for all inputs. Per-method elapsed times exclude pool generation and human response time, so no end-to-end latency or cost claim is made. Final verification checks the software tests, recomputes saved selection outcomes, compares them with CSV/checkpoint fields, and builds the report from unpacked source in a fresh environment.
